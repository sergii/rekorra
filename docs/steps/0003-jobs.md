# Step 0003 — Background Jobs

Status: Ruby 3.3/3.4 CI green; browser and real-worker end-to-end verification pending.

## Demo host application

- Adds Solid Queue 1.6 as a demo-only dependency, with its own SQLite queue database and upstream v1.6 queue schema.
- Adds `OrderReceiptJob < ApplicationJob`: idempotently sets `orders.receipt_generated_at`.
- Adds a host-owned `DemoJobLink` with `order_id` and stable `active_job_id`; no job argument inspection or implicit tenancy inference.
- Seeds an enqueued example for ACME-1001. Workers are **not** started by the web server or CI; the demo may run a Solid Queue worker separately.

## Rekorra engine

- Optional `jobs do` DSL with named source, independent policy and bounded results.
- `Jobs::Registry`, `Jobs::Resolver`, provider-independent `Jobs::Item`.
- `Jobs::Adapters::SolidQueue` maps allowed correlations to queue state (queued, scheduled, running, blocked, failed, finished, unavailable).
- Read-only responsive Jobs panel on Order show, rendered without JavaScript.
- No Solid Queue runtime dependency in published `rekorra.gemspec`, and no Rekorra-owned tables.

## Scope / caveats

- The correlation model is deliberately host-owned. Production hosts must return an association constrained to the **currently scoped record**, not arbitrary jobs.
- The queue backend can purge completed jobs; a now-absent job is shown as `unavailable`, not guessed as successful or failed.
- No unsafe job retries, cancellation, arbitrary job execution or error/argument serialization in the UI.
- No job-attempt history or backtrace display yet; the UI reports provider state, not a complete execution audit.
- Host application decides job retention, queue worker deployment and sensitive-argument filtering.
